# Authentication

Internal `users.id` is the owner of community records. `auth_identities` links email/password, Google, and historical `chatgpt` provider IDs without changing ownership. The PostgreSQL import preserves IDs, PBKDF2-HMAC-SHA-256 password hashes (310,000 iterations), token hashes, and session hashes. No forced password reset or static signing secret is needed.

Registration creates user, password identity, profile, and verification token in one transaction. Verification and password reset consume one-time hashed tokens with their account updates in a transaction. Sessions use random opaque tokens in an HttpOnly, SameSite=Lax, Path=/ cookie. Production cookies are Secure and host-only with a `__Host-` prefix; local development uses a non-Secure local cookie. Session tokens are hashed in the database, expire after 30 days, can be revoked, and are capped at 12 active sessions per account. Verification expires in 60 minutes, reset in 45 minutes.

Google sign-in uses Authorization Code + PKCE, state, nonce, Google JWKS signature verification, issuer/audience/verified-email validation, and safe relative return paths. `GOOGLE_REDIRECT_URI` must use the web origin and `/api/auth/google/callback`. The Next proxy passes OAuth cookies and allows the Google authorization redirect. Existing unverified email identities are revoked before verified Google ownership is linked. New Google users must complete their profile.

Historical hosted-platform identities remain in `auth_identities`, but the public API never authenticates from caller-provided `oai-authenticated-user-*` headers. The proxy and API strip those headers. Legacy hosted-only accounts can now request a one-time password recovery email **if their historical account email was verified and they still control that mailbox**. Reset consumes a hashed, expiring token and creates a local password identity on the same user ID; users who cannot receive this email still require a separate verified identity handoff. Do not trust unverified emails or legacy platform headers as proof of ownership. Production recovery depends on Resend being configured, real delivery tested and the historical mailboxes being reachable; a general automatic account-claim flow is not implemented. Those without accessible verified email remain a cutover blocker. The profile completion and moderation rules still use internal account IDs. Configure `ANIME_CLASH_ADMIN_USER_ID` to the migrated admin user ID.

Mutation routes check same-origin `Origin`/Fetch Metadata and enforce ownership and role checks. CORS allows only `APP_BASE_URL`; production API traffic must carry a short-lived HMAC signature generated by the Vercel Next.js proxy. The Vercel edge overwrites `x-real-ip`; Railway validates the signed address and ignores unsigned client-IP headers. Without a valid signature, the public Railway API refuses requests. Local development uses the direct connection IP. Authentication requests have database-backed rate limits. Never enable `AUTH_DEV_EMAIL_LOG` in production: in local development it can print verification/reset URLs. Production needs Resend `RESEND_API_KEY` and `EMAIL_FROM` for email delivery.

The fixture flow exercises registration, verification, login, authenticated API, logout and revocation; Google provider integration must be checked with real staging credentials and registered callback URLs before cutover.
